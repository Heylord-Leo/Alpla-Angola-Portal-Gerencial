# Version-Mismatch Protection (Phases A–G)

Protects users who keep an **old React frontend** open after a **newer backend** is deployed. Backend
enforcement is the authoritative protection; the frontend monitor + modal are proactive UX.

> Scope: Phases A–G. Phase H (versioned release dirs, IIS physical-path switching, atomic activation,
> maintenance mode, server-wide deploy locks, runner-label changes) is intentionally **not** included.

## 1. Identity model

| Identity | Value | Purpose | Comparison |
|---|---|---|---|
| Source | `gitSha` | exact commit | audit |
| **Logical build** | `buildId = <version>+<shortSha>` (e.g. `2.216.1+372ac47`) | **FE/BE compatibility** | **exact equality only** |
| Binary artifact | `apiArtifact` / `webArtifact` bytes | integrity | manifest equality + (future) SHA-256 |
| Deployment | `deploymentId = <githubRunId>-<githubRunAttempt>` | audit/ops | not compared |

- `buildId` is **environment-independent** (same for TEST and PROD of one commit) and is compared by
  **equality** — **never** ordered (Git SHAs have no ordering). There is intentionally **no**
  `minimumSupportedFrontendBuild`. A future orderable `apiCompatibilityVersion` (date-like, never a SHA)
  is noted for later, not implemented.
- Version authority (unchanged): **`docs/CHANGELOG.md` is authoritative**, `docs/VERSION.md` follows,
  `src/frontend/src/config.ts` is the UI mirror. The deploy workflow validates all three against the
  manual `version` input and fails-closed on any mismatch.

## 2. Metadata plumbing

- **Frontend (compile-time):** `src/frontend/src/buildInfo.ts` reads `VITE_APP_VERSION / VITE_APP_BUILD_ID /
  VITE_APP_SHORT_SHA / VITE_APP_BUILT_AT`, injected by the workflow's frontend build step. Locally (no
  CI vars) it is a clearly-marked `DevelopmentFallback` (`0.0.0-dev` / `DEV-LOCAL`) that never resembles
  a release. **No secrets in `VITE_*`** (they are public).
- **Backend (runtime):** `build-manifest.json` is generated by the workflow into the API artifact and
  read once at startup by `BuildInfoProvider` (`IBuildInfoProvider`, singleton) — the **single runtime
  source of version truth**. The stale csproj/diagnostics literals no longer drive runtime version.
- **`buildMetadataStatus`:** `Valid | DevelopmentFallback | Missing | Malformed | Unknown`.
  - Runtime middleware **fails-open** when status ≠ `Valid` (never self-locks the API).
  - Deployment verification **fails-closed** on `Missing`/`Malformed`/wrong build — TEST/PROD are never
    declared successfully deployed with an invalid/unknown build.

## 3. Backend endpoints

- `GET /api/app/version` — anonymous, DB-free (sibling of `/api/app/environment`). Public fields only:
  `version, buildId, shortSha, environment, builtAtUtc, buildMetadataStatus`.
- `GET /api/admin/diagnostics/version` — authenticated; adds audit fields (`gitSha`, `deploymentId`,
  run IDs, `deploymentStartedAtUtc`). Same provider — no independent version truth.

## 4. Request header + error contract

- `apiFetch` sends on **every** request (reads, writes, multipart uploads):
  `X-Portal-Frontend-Build: <buildId>` and `X-Portal-Frontend-Version: <version>`.
  Untrusted metadata — **never** used for authn/authz. Raw-fetch exemptions (documented): the anonymous
  env probe (`EnvironmentContext`), the version probe (`VersionContext`), and telemetry (`logger.ts`).
- Outdated write → **HTTP 409** RFC-7807 with `code: "CLIENT_VERSION_OUTDATED"` (aligns to the existing
  parser, which reads `code`/`detail`/`correlationId`), plus `currentVersion`, `currentBuildId`,
  `reloadRequired`. `handleApiError` flips the update-required state → blocking modal.

## 5. Frontend monitor, modal, chunk handling

- **Monitor** (`VersionContext`): checks `/api/app/version` on start, on `visibilitychange`→visible, on
  window focus, every **5 min while visible** (paused when hidden), and on a 409. Flags update-required
  **only** when the server returns a `Valid`, **different** `buildId`. A failed probe is transient →
  **never** flags outdated (capped retry cadence via the interval/events).
- **Modal** (`UpdateRequiredModal`): blocking, non-dismissible (no backdrop/ESC), `role="alertdialog"`,
  focus-trapped, dark-mode via CSS variables, Portuguese. **ATUALIZAR AGORA** → `window.location.reload()`
  (a plain reload is sufficient with `index.html` no-cache; no cache-busting query params). It will **not**
  reload on top of an active mutation/upload (`versionSignal` write counter) or unsaved work
  (`reloadGuard`) without a deliberate confirm.
- **Stale chunks:** `installChunkErrorHandler` (main.tsx) listens for `vite:preloadError`,
  `window.error`, `unhandledrejection`; `ErrorBoundary` also routes lazy-import failures. Detection is
  type-first (`ChunkLoadError`, preloadError) with documented message-string fallbacks. A per-build
  one-shot `sessionStorage` marker prevents reload loops.

## 6. Backend enforcement (staged rollout)

Middleware `ClientVersionEnforcementMiddleware` runs **after** `UseAuthentication/UseAuthorization`.
Decision logic is the pure, unit-tested `ClientVersionEnforcement`. Config: `ClientVersionEnforcement:Mode`.

| Mode | Missing header | Malformed | Mismatch | Matching | Reads |
|---|---|---|---|---|---|
| `Disabled` | — | — | — | — | allow |
| `Observe` | log | log | log | log | allow (never reject) |
| `EnforceMismatch` | allow+log | **409** | **409** | allow | allow |
| `EnforceAll` | **409** | **409** | **409** | allow | allow |

- Only **unsafe methods** (POST/PUT/PATCH/DELETE) are enforced. Exempt prefixes: `/api/auth`,
  `/api/app/environment`, `/api/app/version`, `/health`, `/api/admin/logs/ingest`. File **downloads** are
  GET → already exempt; **uploads** are POST → protected.
- Structured logs include method, route, user id, client/server build, mode, environment, correlation id.
  **Never** logs JWTs, bodies, or secrets.
- **Effective rollout defaults (exact):**
  - **DEV → `Disabled`** — from `appsettings.Development.json` (`ClientVersionEnforcement:Mode=Disabled`);
    DEV also runs a `DevelopmentFallback` build identity, so there is nothing to enforce.
  - **TEST → `Observe`** — from base `appsettings.json` (`Mode=Observe`); TEST has no override.
  - **PROD → `Observe`** — from base `appsettings.json`; the server-side `appsettings.Production.json`
    does not set the key, so it inherits `Observe`.
  - Override at any tier via the `ClientVersionEnforcement__Mode` environment variable (IIS app-pool
    setting) — **no redeploy needed**.
  **Promotion:** Observe until valid headers dominate traffic → `EnforceMismatch` → `EnforceAll` once
  missing-header traffic is effectively zero.

## 7. Cache policy (Phase G)

`src/frontend/public/web.config`: `index.html` and `build-metadata.json` → `no-cache, must-revalidate`;
`/assets/*` → `public, max-age=31536000, immutable`.

- **TEST** uses the artifact `web.config` (cache rules shipped in it). The deploy job then **verifies**
  (`Verify web.config cache policy`) that the three `<location>` blocks are present and fails-closed
  before activation if any is missing.
- **PROD** preserves its own server-side `web.config` (port-5002 proxy). The deploy job **patches** it
  in place (`Ensure web.config cache policy`): it adds/normalises the three cache `<location>` blocks
  **without removing any existing rule**, then fails-closed unless both the port-5002 reverse-proxy rule
  **and** all three cache rules are present. The PROD cache policy therefore can never be silently
  absent, and no manual `web.config` edit is required.

## 8. Deployment verification & migration-activation safety

Both `deploy-test.yml` and `deploy-prod.yml`:

- **Build job:** validate version consistency + input (`Validate version and compute build metadata`);
  compute canonical metadata; inject `VITE_*`; write identical `build-manifest.json` into both artifacts
  + public `build-metadata.json` into web; **compute artifact SHA-256** (`Compute artifact SHA-256`),
  writing `artifact-sha256.txt` into each artifact.
- **Two distinct integrity controls** (both required):
  - **Manifest equality** — `api build-manifest.buildId == web build-manifest.buildId == expected`.
  - **Artifact SHA-256** — the runner re-hashes each downloaded artifact folder (deterministic sorted
    `<relPath> <fileHash>` digest, excluding the hash file) and compares to the shipped
    `artifact-sha256.txt`; a mismatch fails the job **before** any server change.
- **Deploy job (corrected order):**
  1. **validate deployment variables** (`Validate deployment variables`) — `TEST_PORTAL_URL` /
     `PROD_PORTAL_URL` must be a present, https, environment-correct host; fails before any server work;
  2. download artifacts;
  3. **manifest equality gate** (FE == BE == expected `buildId`) — before any server mutation;
  4. **artifact SHA-256 gate** (`Verify artifact SHA-256 (integrity)`) — before any server mutation;
  5. **DB readiness + pending-migration gate** — **before** stopping pools / replacing files, so a
     pending-migration failure aborts with the **previous version still live** (never activate new code
     against an un-migrated schema);
  4. backup → stop pools → deploy files → **write deployment metadata**;
  5. **Start pools is `if: success()`** (no unconditional `if: always()` activation);
  6. smoke `/health` → **verify running build identity**: `GET /api/app/version` and `/build-metadata.json`
     must both equal the expected `buildId` (and API == frontend), else the deploy fails;
  7. **availability recovery** step runs only on `failure()/cancelled()` to restart pools (safe because
     migration readiness was validated before the pools were stopped).
- Only cleanup / lock-release / recovery may run under `if: always()`; **activation and success are
  conditional on all gates**.
- Migrations are still applied by the separate `apply-migrations-*.yml` workflows; deploy only **verifies**
  readiness and refuses to activate when migrations are pending. Automatic DB restore is **not** performed
  (forward-only/data migrations) — on an unsafe state, leave the app down and recover manually.
- PROD deploy `timeout-minutes` raised 20 → 45 (slow self-hosted artifact egress, ~121 MB api-artifact).

## 9. Required repository configuration (one-time GitHub setup after merge)

- **Repo variables (Settings → Secrets and variables → Actions → Variables):**
  - `TEST_PORTAL_URL` = `https://portalgerencial-test.alpla.net`
  - `PROD_PORTAL_URL` = `https://portalgerencial.alpla.net`
  These are **fail-fast validated** at the start of each deploy job (present, `https://`, correct
  environment host, not the other environment); the job aborts before any server work if invalid. They
  are public URLs, not secrets.
- **PROD `web.config`:** no manual step — the deploy job patches and validates the cache policy in place
  (see §7).
- **PROD DB connection (existing):** `secrets.PROD_DB_CONNECTION_STRING` (already used) drives the
  migration-readiness gate.

## 10. Troubleshooting stale chunks

A blank route or "ChunkLoadError" after a deploy means the open tab requested a hashed chunk removed by
`robocopy /MIR`. The chunk handler surfaces the blocking modal; **ATUALIZAR AGORA** reloads the fresh
shell (served no-cache). Phase H (staged release dirs) would remove the deletion window entirely.
